When I first architected JARVIS, everything looked perfect on paper. However, as Mike Tyson famously said, "Everyone has a plan until they get punched in the face." The transition from concept to a consistently reliable AI assistant brought several significant engineering hurdles.

## 1. The Latency Problem

In human conversation, a response delay of more than 500 milliseconds feels unnatural. Initially, my pipeline (Wake Word -> Audio Record -> Speech-to-Text -> LLM Inference -> Text-to-Speech) took over 4 seconds. 

To solve this, I had to move away from sequential processing. I implemented audio streaming to the STT engine and started utilizing streaming responses from the LLM. Now, JARVIS begins synthesizing speech for the first sentence while the LLM is still generating the rest of the response.

## 2. Context Window Management

JARVIS runs all day. If I feed every single log, transcript, and terminal output into its context window, it quickly exceeds the token limits and API costs skyrocket. 

The solution was implementing a robust Retrieval-Augmented Generation (RAG) pipeline with Vector Databases. Instead of full memory, JARVIS uses a sliding window of recent conversation and summarizes older interactions, storing them as embeddings. When relevant topics come up, it recalls them dynamically.

## 3. The "Hallucinating Actions" Dilemma

The scariest problem was tool misuse. Early on, JARVIS hallucinated arguments for terminal commands. Once, it tried to run `git push --force` in the wrong directory because it assumed the context.

I had to implement a strict verification layer. Now, any destructive action requires explicit verbal confirmation ("Are you sure you want to delete this folder?"), and the tool registry uses rigorous schema validation before executing any system command.

Overcoming these challenges taught me that building AI applications is less about the model itself and more about the infrastructure wrapping it.
